# Saved-State batched rendering

`saved_state_rendering_42_rtx3090.csv` records the fresh RTX 3090 sweep of all 42 registrations; status distinguishes completed measurements from pending work. `rtx3090_batch_sweep.csv` records each completed batch size. The separate `saved_state_rendering_42_prior.csv` extracts completed 2026-09-28 CPU and A40/L40S measurements at batches 64 and 256. Do not present that earlier table as RTX 3090 data.

Numeric States were saved to NPZ by the source parity campaign. The harness loads those files, verifies their hashes, projects renderer inputs, uploads and constructs batches before timing. Timed calls only render prepared batches and synchronize completion. No simulation stepping, disk reads, State extraction or initial upload occurs inside the timer. Any transfers performed internally by the renderer remain timed. Images remain on the GPU. This is rendering throughput, not end-to-end simulation throughput or a paired speedup over the original simulator.

Fresh batches use up to 16 saved poses from one configuration, repeated to fill the batch. Batches 64, 128 and 256 are required, then sizes double up to 4096 until two consecutive throughput gains are below 5% or allocation fails. The chosen batch is the smallest within 5% of the best measured sweep throughput, with a separate confirmation sample. A throughput plateau does not establish 100% GPU utilization, and MAX_BATCH_NOT_PROVEN_SATURATED explicitly means saturation was not demonstrated. Per-frame time is batch time divided by batch size; SD describes variation across timed batch calls. This is not a 1,000-independent-frame latency distribution.

Batch outputs are checked against individual renders of the same inputs (maximum allowed channel difference 1/255), and renderer input/live-State nonmutation is checked. Source pixel parity is established separately by the prior campaign, not remeasured here. PushT results remain diagnostic. Two symbolic Craftax registrations have no RGB renderer. Fetch PickAndPlace corpus restrictions remain recorded in the scope column. Prior measurements used six repeated poses and 3–30 timed calls; fresh measurements use at least six calls/three seconds per sweep size and ten calls/five seconds for confirmation.

Production source: immutable Oscar `render-parity-df80c9c5-20260928/source-v12`, based on `df80c9c54590afa9fc0482a4dcb241d21f6b63a3` plus the existing renderer overlay. Harness: `scripts/benchmarks/renderer_table/saturation.py`. Oscar job array: 6794187, RTX 3090 constraint. Raw timing samples, input provenance, hardware and per-task harness hashes are retained under `raw-3090/`; exported result hashes are separate JSON files. No production optimization or push is part of this measurement.

## Follow-up explicitly requested by user

Audit and remove avoidable per-environment step loops after this rendering report. Consecutive timesteps depend on previous states; independent batch lanes are the vectorization target. Craftax's scalar JAX dispatch is a candidate for batched/jitted stepping, subject to PRNG, reset and trajectory parity tests. CPU source adapters need evaluation of parallel execution versus alternate simulator backends. Preserve the accepted State/replay semantics and benchmark actual step throughput. This work remains pending and is outside this saved-State rendering experiment.
