All notable changes to this project are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.1.0] - [TODO]

First public release.

### Added

- 80 batched environment classes across classic control, DM Control, Fetch, navigation, OGBench, PushT, PyFlyt Rocket Landing, Roadster, Craftax, Miniworld and MS-Human-700. Most families install as an optional extra, and a missing extra disables only its own family; `snv.import_errors()` names the cause. Fetch needs MuJoCo below 3.12 and a separate Python environment from DM Control, MS-Human, `OGBCube` and `OGBScene`, which need MuJoCo 3.17.
- A class-first API: `snv.CartPole(num_envs=..., device=...)`, plus `snv.make`, `snv.info`, `snv.list_envs` and `snv.list_families`.
- Batched stepping on CPU or GPU. One `step` call takes `(B, A)` actions for one transition or `(B, T, A)` for a sequence, and returns a validity mask instead of resetting finished environments. A step builds intermediate states only for the steps that `states` selects.
- `render(state)` draws frames from a stored state without advancing the simulation.
- `get_state` and `set_state` save and restore a complete TensorDict state. When the batch runs in worker processes, `set_state` checks every batch row in every worker before any worker restores. An invalid state raises and leaves every worker as it was.
- Variation spaces: `sample_variation`, `set_variation` and per-environment reset options, compatible with stable-worldmodel.
- `Env.describe()` reports `state_fields`, the shape and dtype of each state field.
- `visual_fidelity` records, for the classes that declare it, the per-frame MSE against the upstream library as `mse_mean`, `mse_p95` and `mse_max` on the 0-255 scale, and `visual_note` says where the frames differ.
- `snv.tuning`: chunk sizes, Triton block sizes, worker counts and memory budgets are named knobs that you set with `snv.tuning.set`, `snv.tuning.override` or `STABLE_ENVS_<KNOB>` variables. Some defaults come from the GPU's free memory or the CPU's L3 size. Knobs never change frames or state. `cpu3d.render(chunk_size=None)` and `raster2d.render_triton(block=None)` read them too. See [Performance tuning](https://galilai-group.github.io/stable-envs/performance-tuning/).
- `stable-envs tune <Env>` and `snv.tune(env)` measure the fastest knob values for one render path on your machine and cache them. `--show`, `--clear` and `--all` manage the cache.
- A large render on an untuned path logs one `INFO` hint to run `stable-envs tune`. Set `STABLE_ENVS_TUNING_HINT=0` to hide it, or `STABLE_ENVS_AUTOTUNE=1` to tune such a path on first use.
- `stable-envs doctor` checks the driver, Warp and MuJoCo OpenGL setup of each family. It also reports how many render paths are tuned, lists the `STABLE_ENVS_*` variables that are set, flags unknown names and checks torch's compiled GPU architectures.
- [Environment variables](https://galilai-group.github.io/stable-envs/environment-variables/) lists every `STABLE_ENVS_*` variable. An unparseable value raises `ValueError` naming the variable.
- The MuJoCo families (DM Control, Fetch, MS-Human and OGBench) step every environment of a batch in one call: `mujoco.batch` on CPU, and MuJoCo Warp on CUDA by default, with the substeps of a step in one captured CUDA graph. `simulation_backend` selects either one, and `"auto"` uses MuJoCo Warp for CUDA batches of `mjwarp_min_envs` or more.
- On Linux, the families without a batched step run large CPU batches in spawned worker processes, and large render batches draw in render worker processes. The `workers`, `worker_min_lanes`, `render_workers` and `render_worker_min_rows` knobs size the pools without changing the frames.
- On a CUDA device, environments that step in worker processes keep the step bookkeeping on the CPU and move the outputs to the device at the end of `step`.
- **Classic control:** `simulation_backend` steps `CartPole`, `Pendulum`, `Acrobot`, `MountainCar` and `MountainCarContinuous` in one batched float64 operation. By default, CPU batches step in NumPy and the smallest keep the Gymnasium loop, which is faster at that size. There, Gymnasium resets the batch and owns the PCG64 streams, NumPy steps give the same state and outputs as Gymnasium, and Torch steps agree to rounding. CUDA batches step on the GPU in one Triton kernel replayed as a CUDA graph, with resets drawn on the GPU. `"auto"`, `"gym"`, `"numpy"` and `"torch"` select other backends.
- **Classic control:** on CPU, a step does not copy the state into the render rows of the environment. The rows are copied from the simulator when a reader needs them, such as `render()` without a state. The Gymnasium backend builds its state and outputs without TensorDict validation.
- **Classic control:** on CPU, a Numba kernel draws the same primitive records as the Triton kernel, in parallel over frames, and its frames are byte-identical to the Torch path. With `backend="auto"`, small batches of the default appearance draw with the Gymnasium renderer.
- **Classic control:** frames equal the Gymnasium frames even at angles close to a multiple of pi/2. The rasterizer rotates as pygame's `Vector2.rotate_rad` does.
- **DM Control:** 17 classes. On CPU, every environment steps in one `mujoco.batch` call on CPU threads (the `dmc_threads` knob), and the batch copies one compiled model instead of compiling one per environment.
- **DM Control:** on CPU, one Numba kernel draws the frames of every class, shading pixels in the float32 operation order of the Torch renderer. The frames match the Torch frames except for rare pixels where Torch's CPU square root rounds through MKL. `backend="torch"` selects the Torch renderers.
- **DM Control:** `CheetahRun` and `QuadrupedWalk` reset on the `mujoco.batch` threads: their resets are mostly MuJoCo work, and MuJoCo releases the GIL. The other domains reset in one thread, which is faster for their short resets.
- **DM Control:** on CUDA, MuJoCo Warp 3.17 steps all 17 classes by default (`dmcontrol-gpu` extra), with capsule-contact corrections and ordered constraint rows for repeatable replays. `simulation_backend="auto"` uses native physics below a measured cutoff per task, and `"mjx"` keeps Reacher's MJX physics.
- **DM Control:** a mid-episode physics `set_variation()` takes full effect from the next step.
- **DM Control:** `DMCFingerTurnHard` draws the target sphere and the tip site by default, as dm_control's `finger-turn_hard` does. Set `visibility.target` to 0 for stable-worldmodel's default, which hides both.
- The `dmcontrol` and `ogbench-manipulation` extras both pin MuJoCo 3.17 and install side by side.
- **OGBench:** 27 classes. `OGBCube` and `OGBScene` use the OGBench cube size and reset as OGBench does. On CPU, their reset and every step are bit-identical to OGBench, and MuJoCo Warp steps them on CUDA. Their frames have the look of the OGBench pixel tasks that their `reference_id` names.
- **OGBench:** `OGBCube` and `OGBScene` keep a per-environment copy of the NumPy global RNG that OGBench samples tasks from, in the `rng/task` leaves, which lets a seeded reset replay. The arm starts at `agent.ee_start_position` only when the reset options name that leaf or `set_variation` sets it.
- **OGBench:** on CPU, `OGBCube` and `OGBScene` draw with `opengl_fast`, software OpenGL with simplified arm meshes, by default, and `backend="opengl"` draws the source frames. On CUDA, they draw with NVIDIA OpenGL by default, and `supersample=2` or `backend="mjwarp_fidelity"` selects the MJWarp renderer. On Linux, they draw in up to `ogb_gl_workers` processes.
- **OGBench:** the mazes step every environment in one `mujoco.batch` call on CPU, bit-identical to OGBench, and on MuJoCo Warp on CUDA, where PointMaze integrates with Euler. A step stacks its `states` leaf by leaf on CPU. On CUDA, MuJoCo Warp copies the state into one buffer, and the `states` of a step are one copy of these buffers.
- **OGBench:** `PointMazeLargeNavigate` tests its spotlight shadow rays only against nearby walls on CPU, and renders batches of 2048 or more on CUDA.
- **Fetch:** 12 classes. On CPU, one batched call steps every environment, bit-identical to Gymnasium Robotics, and MuJoCo Warp steps CUDA batches by default. `simulation_backend="source"` keeps Gymnasium Robotics' own step, in worker processes for large batches.
- **Fetch:** on CPU, a Numba rasterizer draws the frames by default, with a mean per-frame MSE of about 0.15 against the source. `backend="opengl"` draws them as Gymnasium Robotics does, including the translucent mocap markers, byte for byte at the tested sizes, and draws large batches in render worker processes (the `fetch-opengl` tuning path). Each sky color uploads once per OpenGL context, and a batch with mixed sky colors renders as fast as a uniform one.
- **Navigation:** on CPU, one Numba kernel moves every environment of `TwoRoom`, `TwoRoomTarget`, `Piecewise` and `PiecewiseZones`, with the same float32 rounding as the Torch step. A second kernel draws their dots. `simulation_backend` also accepts `"torch"`, and `TwoRoom` accepts `"jax"`.
- **Navigation:** on CUDA, `TwoRoom` uses JAX dynamics from `jax_min_envs` up (1 by default) and needs the `navigation-gpu` extra. Target distances stay on the device.
- **Navigation:** `PiecewiseZones` and `TwoRoomTarget` draw seeded resets from the same distribution tree as `Piecewise` and `TwoRoom`, which makes `reset(seed=k)` start where stable-worldmodel does.
- **Navigation:** `SimplePointMaze` draws each distinct `info.goal` background once and returns the same goal tensor at every step. Treat `info.goal` as read-only.
- **PushT:** `PushT` and `PushTDiscrete` draw frames byte-identical to pygame with a Numba rasterizer on CPU and, when Triton is installed, Triton kernels on CUDA. Frames with action markers, unsupported shapes or a coordinate near a rounding midpoint fall back to pygame. `backend` takes `"auto"` or `"source"`.
- **PushT:** a port of the Pymunk contact solver steps every environment in one call: in Numba in float64 on CPU, in Triton in float32 on CUDA, or in JAX (`simulation_backend`). The state holds the solver cache, so `set_state` restores without a replay. On Linux, large batches reset and render in worker processes (the `pusht-sim` and `pusht-render` tuning paths).
- **PushT:** continuous actions outside [-1, 1] are accepted, as stable-worldmodel accepts them. `PushTDiscrete` indices must be in [0, 16).
- **PushT:** a bad `render(out=)` buffer raises an error saying that the buffer must be contiguous and match the frames in shape, dtype and device.
- **PyFlyt Rocket Landing:** on CPU, the physics worker processes draw step frames with TinyRenderer, and render worker processes draw batches of stored states. One process holds at most 1022 environments, and larger batches use more processes on every platform.
- **PyFlyt Rocket Landing:** a reset or a restore replaces the PyBullet client of one environment at a time, so a worker process holds at most one client more than its environments. A large state leaf that is all zero, such as `current/wrapper/current_goal` without a render mode, isn't stored for each environment. A reset checks the arguments of every environment before it changes one, and a failed restore replays the states it replaced, so no environment changes. With frames on CUDA and 8 cores of an L40S pod, the peak host memory is 37.0 GB for 1024 environments and 70.0 GB for 2048, where the PyFlyt source in 8 worker processes uses 37.5 GB and 70.6 GB.
- **PyFlyt Rocket Landing:** on CUDA, the renderer draws the fins, legs and fuel tank at the current body pose, picks ground texels as TinyRenderer does, and hides the ground when the camera is below it. The mean per-frame MSE against PyFlyt is 4.2.
- **PyFlyt Rocket Landing:** the flame changes color at ignition, and reset saves and restores the engine around the goal render, as the PyFlyt pixel environment does.
- **Roadster:** `RoadsterLoop`, `RoadsterMission`, `RoadsterTrafficJam`, `RoadsterRooftop` and `RoadsterCarHop` are five planning tasks for a jet-powered car in MuJoCo (`roadster` extra). They have a complete state with `weather.wind` and `weather.rain` physics leaves.
- **Roadster:** MuJoCo's OpenGL renderer draws the world-model camera, on the GPU with its EGL driver and on the CPU otherwise. The visual variation leaf `rendering.cinematic` draws the same state on a dark-space scene with shadows and MSAA. The exhaust smoke comes from the exhaust history in state (`fx`), which lets `render(state)` show it.
- **Roadster:** large CPU batches step in worker processes and draw in render workers (the `roadster-sim` and `roadster-render` tuning paths).
- **Craftax:** `CraftaxClassicPixels`, `CraftaxClassicSymbolic`, `CraftaxPixels` and `CraftaxSymbolic` run the upstream JAX simulator with the whole batch in one jitted `vmap` (`craftax` and `craftax-gpu` extras).
- **Miniworld:** `MiniWorldMovingBlockWorld` runs the 3D Dynamic Blockworld of Flow Equivariant World Models (`MovingBlockWorld` from the hlillemark/Miniworld fork's `flowm_release` branch) with a complete state, and draws Miniworld's own OpenGL agent view (`miniworld` extra).
- **Miniworld:** `preset="flowm"` (the default) is the paper's dynamic dataset, `preset="flowm-textured"` its textured split and `preset="upstream"` the registered environment. Each episode of the FloWM presets draws 6 to 10 blocks, and state pads them with a `blocks.present` mask.
- **Miniworld:** one batched step moves every environment, in Numba on CPU, bit-identical to the fork, and in Triton on CUDA. Large batches draw `render(state)` in render workers (the `miniworld-render` tuning path).
- **MS-Human-700:** `MSHumanLocomotion` wraps the whole-body musculoskeletal locomotion model (`mshuman` extra). `mujoco.batch` steps it on CPU and MuJoCo Warp on CUDA, the float32 state lives on the environment's device, and MuJoCo's OpenGL renderer draws the frames. On CPU, a step stacks its `states` with the shared core stack on one Torch thread.
- **MS-Human-700:** the Apache-2.0 model downloads from LNSGroup/MS-Human-700 at a pinned commit on first use. Set `STABLE_ENVS_MSHUMAN_HOME` to use an existing checkout.
- Comparison tests check each environment against its upstream library and against stable-worldmodel, for state, simulation, tasks and pixels.
- The tests compare frames with a recorded source MSE for each class (`tests/fixtures/source_mse.json`) and with golden frames of the project's own renderers (`tests/fixtures/golden/`).
- `stable_envs.testing` measurement helpers, the `benchmarks/` harness, including `benchmarks/dmc_mjwarp.py` for native and MuJoCo Warp DM Control physics, and the MkDocs documentation.
- LeWM world-model training example in `examples/lewm`.

For known gaps, see the Limitations section of each [environment page](https://galilai-group.github.io/stable-envs/environments/).
